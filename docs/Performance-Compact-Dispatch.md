# 同步分发数据紧凑化与初始化整理

日期：2026-11-20。基线为 `sync` 的 `b9373dd`，五项逐一实现并测量后，撤回稀疏表平坦化；最终提交见下文。
本轮仍使用同步、固定生命周期的框架，不包含主干异步端点；公开调用方式、完整
`RegAccessInfo` 字段与复制语义、动态 resolver 结果和紧凑快照格式保持不变。

## 实现与范围

| 阶段 | 提交 | 改动 |
|---|---|---|
| C1 | `dd10785` | 字表只保留四个 32 位字段，坐标按需借用实体布局 |
| C2 | `2fb179e` | 实体坐标、最终映射地址、名称分别连续存储 |
| C3 | `a3877e6` | 紧凑 View 二分键、无交叠入口、每 View 的 Reserve 索引切片 |
| C4（撤回） | `a56ab56` | 平坦开放寻址候选测出稀疏访问回退，最终保留 unordered_map |
| C5 | `fd69444` | 页目录懒分配、几何指纹分桶、连续 claims 合并和 Reserve 校验剪枝 |

`PreparedAccessInfo` 从本次平台的 56B 降为固定 16B，字项负载减少 71.4%。没有压缩
ordinal 或 linear 的位宽，也没有把多维坐标反算搬到每次 MMIO。普通无回调读写在
读取实体坐标前返回；回调、派生及诊断从实体布局中借用已有坐标。

C2 将坐标步距从本次平台的 80B 缩为 40B。每元素的地址、坐标和字符串对象总量没有
因此减少；每个布局额外增加两个 vector 头及其配置期分配。最终映射地址与声明时的
局部地址仍独立保存，切片、别名和地址查询沿用原语义。

C3 的 Reserve 切片只保存全局 Reserve 下标。命中 View 后，仅检查与它的范围相交的
Reserve，并继续按命中 mount 的 scope 比较优先级。成本为 O(R_view)，索引总量是
所有 View 相交数量之和；不宣称任意布局都变成常数时间。重叠入口仍处理透明空洞及
原优先级，identity 目标资格检查复用同一份静态范围信息。

C4 已撤回。使用两次乘法混合 64 位地址的平坦表在 64B stride、64 个 View 的配对测量中，
读写比上一阶段慢约 26% / 36%。改为单次乘法取高位虽降低哈希本身的成本，却会让合法
规则步长聚集：128 个元素、3948B stride（跨度约 0.5MiB）平均探测 57.37 次。
独立整数模拟覆盖 6,144 组合法布局后也否决了简单 xor 补丁，因此保留已有
unordered_map，未增加多种哈希模式、调参或运行期缓存。高位地址、未命中与共享布局的
回归用例保留。后续整理 `b6b0c38` 把 Reserve 切片范围直接放在已命中的 EntityView 上，省去
反向求 View 下标；View 搜索元数据与绑定元数据合计占用不变。

C5 的几何指纹只用于缩小候选集合，命中后仍精确比较几何，避免哈希碰撞导致错误共享。
连续数组按 stride 排序后逐轴证明紧密覆盖，支持转置连续矩阵；仅比较总跨度不足以
排除重复地址和空洞。Reserve 安装校验使用临时前缀最大 end 跳过无关 mount。

相对基线，生产源码（src + include，含注释）净增 142 行，新回归增加 262 行。本阶段
减少数据冗余、分配及扫描，尚未收敛标量访问引擎或回调 ABI。`Interleaved2` 及现有
Table 容量边界保留，未引入逐字 constexpr 建表。

## 功能验证

C1 至 C5 每阶段均以 GCC 14.2、Release、`-O3 -DNDEBUG -Wall -Wextra -Werror`
构建，并通过全部 35 项 CTest。新增覆盖包括坐标与地址分离后的切片和 info 复制、
多个入口/VF 的局部 Reserve、透明空洞、128 个 1 TiB 跨步稀疏元素、最大合法字地址、
重复未命中、懒分配表生命周期、转置连续数组及跨度相同但重复/有洞的形状。

最终代码为 `ff6867e`，在 C4 撤回后重新验证：GCC 严格 Release 的 35 项 CTest、
Clang 19.1.7 严格 Release 的 35 项 CTest，以及 GCC 14.2
的 ASan/UBSan 构建及 35 项 CTest 均通过（`-O1 -g`、非 PIE、开启泄漏检测和错误即停）。安装包的
独立三翻译单元消费者编译、链接、运行通过。同口径 `nm -g` 的强定义符号 T/D/B/R 均为
217 个，无增删；头文件和库仍须配套重编译，不将这个符号数量作为跨工具链 ABI 保证。

性能测量用最终 GCC 静态库 SHA256：
`0b4b41618687cd1bf40700325ff2946c89e9d7a391b1b4b8fd2fa010a4b4e8a4`。

## 测量口径

每阶段保存匹配提交的头文件和 GCC Release 静态库；不使用 LTO。构建及功能验证完成后，
才在固定 CPU 上交替运行对照进程。各基准验证返回值、回调计数和最终存储；只比较同一
测量场景中的版本，不将裸数组循环与完整 MMIO 的比值解释为框架调度倍数。

内存测试构造真实 RegisterBank。原 `entityhash_memory.cpp` 是独立容器实验，不能单独
证明框架字表的变化。共享表统计、分配器占用与进程峰值 RSS 分别记录；共享表节点的
估算值不视为精确堆内存。最终版本仍使用原稀疏容器；中间候选的数据单独标记。

## 最终配对结果

Intel Xeon Platinum 8573C，GCC 14.2，CPU 1，线程 CPU 时间。最终版本相对
`b9373dd` 跑 48 个场景、4 轮交替配对（384 个进程）；对疑点另外跑每进程 2000 万次、
8 轮配对（160 个进程）。全部数值校验通过。以下为中位数，单位 ns/次；负变化表示更快。

| 场景 | 基线 | 最终 | 变化 |
|---|---:|---:|---:|
| 64 View、连续地址、无回调读 | 22.15 | 19.69 | −11.1% |
| 同上，写 | 20.77 | 18.57 | −10.6% |
| 64 View、64B 稀疏步长、无回调读 | 26.56 | 23.45 | −11.7% |
| 同上，写 | 25.23 | 22.10 | −12.4% |
| 64 View、128 个无关 Reserve、无回调读 | 134.48 | 19.23 | −85.7% |
| 同上，另有每 View 一个局部 Reserve，读 | 152.32 | 23.80 | −84.4% |
| identity + index、无回调读 | 76.12 | 73.47 | −3.5% |
| 同上，无回调写 | 73.27 | 69.89 | −4.6% |
| identity + index、有回调读 | 79.87 | 76.68 | −4.0% |
| 同上，有回调写 | 74.46 | 71.73 | −3.7% |
| identity + index、回调及两层 pre_access，写 | 81.88 | 77.00 | −6.0% |

Reserve 的大幅收益来自消除全局扫描，不能推广为任意 MMIO 都有数倍收益。
identity/index 场景仍逐次求值；最终相对同轮手写范围判断 + switch 的中位数比值为
约 1.73～1.97 倍，本轮没有消除这部分差距。单 View 无回调也没有 64 View 那样的稳定
两位数收益：例如 AddressSpace 标量读写四轮中位数约为 12.72→12.63、10.09→10.06ns。

**存在明确回退，不能称为全面提速。** 长循环复核如下：

| 场景（读，除最后一行） | 基线 | 最终 | 变化 | 最终更慢的配对数 |
|---|---:|---:|---:|---:|
| 直接映射入口、轻量回调 | 11.30 | 11.59 | +2.6% | 7/8 |
| 直接映射入口、完整 info 回调 | 12.54 | 13.51 | +7.8% | 8/8 |
| AddressSpace、轻量回调 | 14.40 | 15.14 | +5.2% | 8/8 |
| AddressSpace、完整 info 回调 | 16.70 | 17.35 | +3.9% | 7/8 |
| 4096 元素、完整 info 回调 | 16.66 | 16.91 | +1.5% | 6/8 |
| 64 View、1 TiB stride、有回调读 | 43.25 | 45.11 | +4.3% | 7/8 |
| 同上，写 | 38.32 | 38.88 | +1.5% | 7/8 |

去掉共享字表坐标后，Formula 回调改读各实体的坐标数组，多一条依赖读取，且多实体
访问会覆盖更多缓存行，这是合理的成本来源假设，尚未逐项消融证实；不意味着每次新增完整坐标或 info 复制。
直接映射入口原本就访问实体坐标，其小幅回退的具体指令级原因尚未证实。此次保留
紧凑记录及主要分发/内存收益，同时完整披露上述取舍，未为单个基准添加特殊分支。
在本基准循环中，句柄原生访问仍在亚纳秒量级，此轮不把这些小幅波动作为句柄优化结论。

## 初始化与内存

`storage4096`、`dag-full` 和 POE 初始化基准每个进程运行三次，表中取进程内中位数，
再跨四轮配对取中位数，不能解释为首次设备初始化。其余内存场景每进程只构造一次。
下表的实例数指 RegEntityBundle 实例，例如两个寄存器数组对应两个寄存器实体节点。

| 真实 bank 场景 | 构造 ms，前→后 | finish ms，前→后 | finish 后分配器占用 B，前→后 | 峰值 RSS KiB，前→后 |
|---|---:|---:|---:|---:|
| 9 个 Bundle 实例，每份两个 8192 元素 u32 数组 | 46.52→34.88 | 0.052→0.047 | 38,237,600→21,144,240 | 60,464→43,818 |
| 9 个 Bundle 实例，每份两个 1024 元素 u512 稀疏数组 | 14.17→12.72 | 0.044→0.041 | 23,087,296→22,041,568 | 31,020→29,982 |
| 显式 4 GiB 地址空间、64 个 Bundle 实例、9 个映射入口 | 21.73→5.00 | 3.090→0.099 | 25,270,800→4,820,144 | 28,904→17,144 |
| storage4096：9 个 Bundle 实例，每份十个数组 | 86.42→41.14 | 0.066→0.054 | 本基准不采集 | 100,302→60,436 |
| 完整静态 PF/PF_VF/VF 的 POE 形状 | 2.201→2.173 | 0.607→0.533 | 3,545,344→3,319,552 | 17,144→17,144 |

首轮冷构造单独比较：`storage4096` 为 **188.016→52.198ms**，4/4 轮更快；
完整 POE 形状为 **4.395→4.779ms（+8.7%）**，4/4 轮更慢。因此不能宣称所有设备
首次初始化都加速。冷构造指标也保存在机器记录的 `cold_init_ns` 中。

POE 形状的 Summary 格式化为 0.278→0.232ms，Full 为 15.630→15.809ms；大 u32 数组
Summary 为 0.071→0.096ms，Full 为 46.064→45.591ms。诊断输出继续生成完整信息，
没有通过关闭日志或省略名字获得初始化收益。峰值 RSS 含校验和报告阶段，不能与
finish 后分配器占用混为一项。宽稀疏数组的构造只有 2/4 轮变快，不作为稳定提速承诺。

连续 claims 合并只帮助已证明连续的布局；稀疏布局不保证初始化更快，例如有局部
Reserve 和回调的稀疏读场景，构造中位数 13.89→15.01ms、4/4 轮更慢。
显式 4 GiB 场景受益于不再预分配两个未使用的页目录，其收益也不能外推到所有 bank。
没有运行私有 QEMU、TM/DROP 或 POE 端到端套件，以上不是生产设备耗时预测。

全部阶段、最终对照及复核的机器记录见
[results-compact-dispatch-20261120.json](../benchmarks/results-compact-dispatch-20261120.json)。
其中 `final-paired` 是撤回前的中间候选，部署结论只使用 `corrected-final-paired` 和
`corrected-scalar-confirm`。构建与复现命令见 [基准入口](../benchmarks/README.md)。
